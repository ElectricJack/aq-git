# AQ integration contract

System-level ownership and product packaging are defined in [AQ ecosystem and releases](../../aq-server/docs/architecture/0001-ecosystem-and-releases.md). [Execution and recovery](../../aq-server/docs/architecture/0002-execution-and-recovery.md) defines caller-side assignment authority, cancellation and retry policy; it does not change this component's local retention or Git operation guarantees.

The standalone binary works without AQ, a database, inbound worker RPC, or a hosting account. AQ owns enrollment, authenticated outbound communication, assignment generations, scheduling, worker confinement and authorization. aq-git owns local repository evidence, retained objects and conditional Git operations. The included fake coordinator demonstration is a local process integration fixture; it does not establish a deployed AQ adapter. The deployed adapters live in the consumers: as of 2026-11-12 aq-server runs v0.2.0 as its supervised `aq-git` compose service and aq-worker prepares every source workspace through its pinned copy, both on the local `aq-ms1` stack (aq-server `docs/status.md`).

A runtime starts `aq-git --state-dir ROOT --listen SOCKET serve` explicitly, waits for socket readiness, and requests `capabilities`. The root/socket and central credentials belong to the runtime identity. Agents receive only their configured workspace grants. Cooperative same-identity confinement is reported honestly; the socket API is a trusted local-process boundary.

The worker polls outward for an authenticated assignment containing repository UUID, logical identity, binding generation, base OID, attempt correlation and transfer information. It explicitly registers a worker binding or adopts a newer generation through a drained binding update. An artifact cannot update a binding. A stale generation is a conflict, and live work is never silently relabeled.

AQ stages a downloaded artifact in the runtime's bounded incoming area and submits an explicitly mapped `artifact.import` request. The current local transport convention places `manifest.json` and optional `objects.bundle` under `ROOT/artifacts/incoming/<artifact_handle>/`; exported files are under `ROOT/artifacts/<artifact_handle>/`. These paths are runtime staging integration points, not grants for an agent to edit repository metadata. Transport copies only completed manifests/bundles, validates authenticated assignment context independently, and publishes the incoming directory only after download completion. aq-git validates digest, identity, generation, prerequisites, connectivity and quotas before issuing a retained receipt. AQ must not infer central durability from an upload finishing alone.

A worker creates an independent workspace at the frozen base. The harness stops writers before checkpoint or retirement, obtains a retained checkpoint source, and exports a source artifact. The worker posts progress and uploads completed bytes through AQ's outbound channel. The central runtime stages and imports them, then returns the central durable retention receipt through AQ. Once this receipt is acknowledged, central candidate construction no longer depends on the worker remaining online.

The coordinator explicitly maps approved source receipt IDs and OIDs into ordered `candidate.create` inputs. A conflict returns bounded paths and a retained clean prefix for repair through a new attempt. An approved ready candidate is published by the central runtime with the configured target and explicit expected old OID. Worker mode rejects publication. Test/check approval remains AQ policy; opaque task IDs never authorize publication.

The adapter must define a whitelist for each authenticated exchange. For example, a source-upload message maps assignment repository UUID and binding generation from trusted assignment state, maps the staged artifact handle from transport state, allocates a durable import operation UUID, and permits only `artifact.import`. It never forwards a worker-supplied arbitrary operation or JSON object to the central socket. Before publication, authorization maps an approved candidate UUID, configured branch and expected revision into `publish`; credentials and remote URLs come from the binding.

Three separate facts are reported outward: source retained centrally, AQ attempt accepted, and candidate publication outcome. A stale assignment may upload valid objects which AQ declines to use. Import success does not mark a task complete. An `applied` receipt remains historical if the branch later moves; current reachability requires a separate explicit observation/query. `already_present` establishes observed presence without claiming this invocation caused a write.

On socket loss, reconnect and reuse operation UUIDs. A dispatched publication with missing acknowledgement remains indeterminate and blocks the destination. AQ requests `operation.reconcile` under a new command operation UUID, using the target record generation returned by `operation.show`. Reconciliation never re-pushes. If presence is not established, only explicit operator resolution after stopping old publishers can authorize another operation; the historical ambiguity remains recorded.

Cleanup follows durable ownership: obtain the central receipt, retire the clean stopped workspace, release local checkpoint/transfer handles no longer needed, then request worker pool eviction with the expected storage generation and reconstructible assertion. Refuse cleanup while dependents remain. Artifact upload success, worker disappearance and task completion are not retention-release signals.

A parent-only engine crash is handled by the internal lifecycle guard, which retains root ownership while real Git and forked helpers are killed and reaped. A guard crash leaves a durable active-incarnation fence. The runtime must stop the old local execution environment, gather cleanup evidence, and use audited direct `recovery clear-fence` with the exact incarnation before restarting mutations. This local cleanup cannot resolve a remote push; reconciliation remains separate.

Use [`api.md`](api.md) for exact request shapes and limits. Run the standalone correctness/process fixtures and fake coordinator demonstration before replacing any local harness with an AQ transport adapter. Actual AQ authorization, polling, network transfer and stale-attempt acceptance require their own adapter tests and deployment evidence.

The process demonstration is executable with `cargo test -p aq-git-cli --test scenario`: it runs two socket services, transfers a retained base, checkpoints worker edits, imports the source centrally, deletes the entire stopped worker volume, then builds and publishes from central retention alone.
